# Приложение Г. Статистика пилотной обработки 40 методик

Агрегированные показатели пилотной обработки используются для проверки гипотезы H3. Новая методика сопоставляется с уже формализованными фрагментами, после чего каждый фрагмент обрабатывается в одном из трёх режимов.

Имена режимов `copy`, `patch` и `agent` сохранены как технические метки эксперимента. `copy` означает прямое переиспользование совпадающего фрагмента, `patch` — локальную адаптацию найденного прототипа, `agent` — полный перевод фрагмента агентной моделью.

## Г.1 Состав пилотной обработки

Пилотная обработка охватывает 40 новых методик Solactive и стартовый прогон, использованный как первая точка накопления пула прототипов. Поэтому в статистических расчётах динамики накопления используется 41 рабочее пространство, а в основном тексте результат обозначается как пилотная обработка 40 методик.

**Таблица Г.1 — Состав пилотной обработки**

| Показатель | Значение |
| --- | ---: |
| Фрагменты, учтённые в статистике | 1 973 |
| Фрагменты в режиме `copy` | 1 369 |
| Фрагменты в режиме `patch` | 373 |
| Фрагменты в режиме `agent` | 231 |
| Доля прямого копирования \(R_{\text{copy}}\) | 69,4 % |
| Доля переиспользования \(R_{\text{reuse}}\), `copy+patch` | 88,3 % |
| Фрагменты, потребовавшие LLM-вызова | 30,6 % |
| Суммарный расход LLM-токенов | 2 018 300 |
| Средний расход LLM-токенов на методику | 50 458 |
| Время выполнения при четырёх параллельных батчах | около 3 часов |

Две величины в таблице имеют разный смысл. \(R_{\text{copy}}\) показывает долю полностью совпадающих фрагментов, которые можно перенести без генерации нового IR. \(R_{\text{reuse}}\) шире: он учитывает и прямое копирование, и локальную адаптацию уже имеющегося прототипа.

## Г.2 Динамика переиспользования по батчам

Методики обрабатывались четырьмя батчами. Каждый следующий батч имел больший пул уже формализованных прототипов; это увеличивает долю режима `copy` и снижает долю полного агентного перевода.

**Таблица Г.2 — Динамика переиспользования по батчам**

| Батч | Размер пула прототипов | `copy` | `patch` | `agent` | LLM-токены на методику | Время на методику |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A | 1 | 42,6 % | 30,2 % | 27,2 % | 98 277 | 2 415 с |
| B | около 12 | 71,5 % | 19,4 % | 9,2 % | 41 144 | 982 с |
| C | около 22 | 77,2 % | 16,2 % | 6,7 % | 33 898 | 814 с |
| D | около 32 | 82,7 % | 12,7 % | 4,6 % | 22 523 | 506 с |

От батча A к батчу D доля прямого копирования выросла на 40,1 процентного пункта. Одновременно средний расход LLM-токенов на методику снизился в 4,4 раза, а среднее время обработки методики — в 4,8 раза. Это соответствует ожидаемой динамике: по мере накопления прототипов повторяющиеся фрагменты чаще закрываются через переиспользование.

| --- | ---: | --- |
| Spearman \(\rho\), размер пула — доля `copy` | 0,771 |
| Число рабочих пространств в расчёте Spearman | 41 |

Положительное значение \(\rho\) означает, что при росте пула прототипов доля фрагментов, обработанных через `copy`, монотонно увеличивается.

**Таблица Г.4 — Попарное сравнение батчей по доле прямого копирования**

| Сравнение батчей | Значение \(p\) |
| --- | ---: |
| A против B | 0,00115 |

Различия между ранним батчем A и последующими батчами статистически выражены. Это подтверждает, что рост переиспользования связан не только с отдельными удачными методиками, а с накоплением корпуса прототипов.

## Г.4 Проверка качества переиспользования

Переиспользование прототипов проверялось двумя слоями: детерминированными проверками всех обработанных рабочих пространств и стратифицированной LLM-оценкой выборки. Детерминированные проверки охватывают 42 рабочих пространства, поэтому число проверенных фрагментов больше, чем 1 973 фрагмента пилотного среза.

Имена вердиктов сохранены как технические метки оценки: полное соответствие (`corresponds`), частичное соответствие (`partially_corresponds`) и отсутствие соответствия (`does_not_correspond`).

В режиме `copy` не найдено ни одного случая `does_not_correspond`; этот результат используется при интерпретации прямого переиспользования.

## Г.5 Порог прямого копирования

В финальной конфигурации прямое копирование разрешается только для фрагментов с нулевой дистанцией после нормализации. Технически это задаётся порогом `COPY_THRESHOLD = 0.0`.

Такой порог исключает перенос IR при малом, но содержательном изменении текста: например, при замене числового ограничения или изменении множества допустимых объектов. После фиксации порога 94 пограничных фрагмента были переведены из режима `copy` в режим `patch`, то есть вместо прямого переноса прошли локальную адаптацию.
